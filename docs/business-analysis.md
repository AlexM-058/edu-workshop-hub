# Business Analysis: Edu Workshop Hub

## 1. Project Objective

The project aims to build a centralized web platform for organizing, publishing,
enrolling in, and managing educational workshops for teachers.

The system must support:

- Role-based application layouts.
- Workshop enrollment.
- Automatic waiting list promotion.
- Attendance tracking.
- Official document generation.
- Bilingual interface support for Romanian and German.

## 2. Application Roles

The platform has three main application layouts:

- Professor
- Referent
- Admin

## 3. Professor Layout

The professor is the end user who participates in workshops.

Main capabilities:

- Log in.
- View active workshops.
- See workshop details:
  - title
  - referent
  - date
  - location
  - available seats
- Enroll in a workshop.
- Withdraw from a workshop.
- Join the waiting list when the workshop is full.
- See personal enrollment status:
  - confirmed
  - waiting list
- Download a participation certificate after attendance is confirmed by the
  referent.

## 4. Referent Layout

The referent is the workshop organizer.

Main capabilities:

- Create workshops.
- Edit workshops.
- Delete workshops.
- Configure workshop data:
  - title
  - description
  - capacity
  - date
  - location
- View confirmed participants.
- View waiting list participants.
- Mark teacher attendance.
- Generate attendance lists as PDF or Excel.

## 5. Admin Layout

The admin supervises platform data and users.

Main capabilities:

- Create and manage referent accounts.
- Create and manage professor accounts.
- Manage workshop or course categories.
- Manage Romanian and German translations.
- View global platform activity.
- Review audit information.

## 6. Key Business Logic

### 6.1 Automatic Waiting List

When a confirmed participant withdraws from a workshop:

1. The confirmed participant is removed from the participant list.
2. One seat becomes available.
3. The system searches the waiting list for that workshop.
4. The first waiting list entry by enrollment timestamp is selected.
5. That teacher is moved from waiting list to confirmed participants.
6. The system sends an email notification to the promoted participant.

Important rule:

- Waiting list order is first come, first served.

### 6.2 Bilingual Interface

The system must support Romanian and German.

Requirements:

- The user can switch language from a global selector.
- Static UI labels must be translated.
- Menus, buttons, tables, and status labels must use the selected language.
- Admins should be able to manage translations in a later phase.

### 6.3 Document Generation

The platform must generate official workshop documents.

| Document | Generated By | Condition |
| --- | --- | --- |
| Attendance list | Referent | Can be generated during or after the workshop. |
| Participation certificate | Professor | Can be downloaded only after attendance was confirmed. |

Expected formats:

- Attendance list: PDF and Excel.
- Participation certificate: PDF.

## 7. Non-Functional Requirements

Security:

- Passwords must be encrypted.
- Sessions must be secure.
- Users must only access features allowed by their role.

Responsiveness:

- The platform must work well on desktop.
- The platform must work well on tablet.

Performance:

- PDF generation should take less than 3 seconds for normal workshop sizes.

Internationalization:

- Romanian and German must be supported from the beginning of product design.

## 10. Next Product Decisions

Before implementing the first feature, the team should confirm:

- Exact fields required for a workshop.
- Exact user profile fields for professors and referents.
- Whether certificates need a fixed official template.
- Whether attendance lists need signatures.
- Whether email notifications are required in the MVP or can be added later.
- Whether German translations are manually managed or stored in files first.
